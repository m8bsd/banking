# Instagram-like MySQL Schema

A simple relational database design for an Instagram-style social app: users, follows, posts with multi-image carousels, comments (threaded), likes, hashtags, stories, saved posts and direct messages.

## Requirements

- MySQL 8.0.16+ (needed for `CHECK` constraints and expression defaults)

## Project structure

| File          | Purpose                                              |
|---------------|------------------------------------------------------|
| `schema.sql`  | Creates the `insta_clone` database, tables and views |
| `seed.sql`    | Sample data (5 users, posts, likes, comments, etc.)  |
| `queries.sql` | Example queries: feed, profile stats, suggestions    |

## Quick start

```bash
mysql -u root -p < schema.sql
mysql -u root -p < seed.sql
mysql -u root -p < queries.sql
```

Or, from the MySQL shell:

```sql
SOURCE schema.sql;
SOURCE seed.sql;
SOURCE queries.sql;
```

> `schema.sql` drops and recreates the `insta_clone` database, so don't run it against data you want to keep.

## Entity relationships

```
users ──< posts ──< post_media
  │         │──< comments (self-ref parent_id for replies) ──< comment_likes
  │         │──< post_likes
  │         │──< saved_posts
  │         └──< post_hashtags >── hashtags
  │──< stories
  │──< messages (sender / receiver)
  └──< follows (follower / followee, both -> users)
```

## Tables

| Table           | Description                                                        |
|-----------------|--------------------------------------------------------------------|
| `users`         | Accounts: unique username/email, bio, avatar, private flag         |
| `follows`       | Follower → followee. `status` is `pending` for private accounts    |
| `posts`         | A post with caption and optional location                          |
| `post_media`    | Images/videos for a post, ordered by `position` (carousel)         |
| `comments`      | Comments on posts; `parent_id` supports threaded replies           |
| `post_likes`    | One like per user per post (composite primary key)                 |
| `comment_likes` | One like per user per comment                                      |
| `hashtags`      | Unique tags                                                        |
| `post_hashtags` | Many-to-many link between posts and hashtags                       |
| `stories`       | Short-lived media; `expires_at` defaults to 24h after creation     |
| `saved_posts`   | Bookmarked posts                                                   |
| `messages`      | Direct messages between two users with a read flag                 |

### Views

- `v_post_stats`: like and comment counts per post
- `v_user_stats`: post, follower and following counts per user

## Design notes

- **Composite primary keys** on join tables (`follows`, `post_likes`, etc.) prevent duplicate likes/follows without extra unique indexes.
- **`ON DELETE CASCADE`** removes dependent rows automatically, e.g. deleting a user removes their posts, comments and likes.
- **Self-follow is blocked** with a `CHECK` constraint.
- **Indexes** cover the common access paths: a user's posts by date, comments per post, reverse lookups on follows/likes, and unread messages.
- **Counts are computed** via views instead of stored counters. This keeps the schema simple; for large scale, consider denormalized counter columns updated by triggers or application code.
- **Passwords** must be stored as hashes (bcrypt/argon2) generated by your application. The seed values are placeholders.
- **Expired stories** are not deleted automatically. Filter on `expires_at > NOW()` or schedule a cleanup (MySQL `EVENT` or cron).

## Ideas for extending

- Notifications table (likes, comments, follows)
- Post tags / user mentions
- Blocked users and muted accounts
- Reels, highlights, and story views
- Group conversations (replace `messages` with `conversations` + `participants`)
- Full-text index on `posts.caption` for search
